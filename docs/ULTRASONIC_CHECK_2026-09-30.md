# 超声波无信号检查（2026-09-30）

后续蓝牙已换为 JDY-31 SPP；当前测距记录工具使用 `--port <出站 COM>`，旧 BT24 的 `--ble` 仅供旧模块。接口与连接步骤见 [模块更新说明](MODULE_UPDATE_2026-09-30.md)。

收到“超声波没有信号”的反馈后复查驱动。本次没有连接开发板或示波器，无法确认实物根因；以下记录区分代码中已确认的问题与下午需要测量的信号。

## 软件检查与修正

- 原驱动在没有上升沿且 Echo 低时上报有效 6000 mm。这会掩盖断线、模块未供电或捕获失效。现在所有未完成的 Echo 均无效，自动状态机会暂停或故障；超量程也会无效，待 HC-SR04-P 实物资料和输出行为确认后再决定是否需要明确的超量程策略。
- 微秒延时依赖 TIM10；原循环在计数器停止后永远不退出。现在等待有上限，启动时检查计数是否前进，运行中检测到延时故障时清测距有效位、关闭电机，并禁止该故障下重新应用驱动输出。该异常会锁存为 fault=6、HW 0 CLOCK；STOP 不清除故障，修正原因后需重新初始化/上电。
- 拒绝 30 ms 截止时间以后的回调和 CC1 过捕获，避免迟到/覆盖的捕获组成假距离。保留新尝试期间上一有效距离，在尝试失败时立即判无效。
- 每轮主循环最多处理两条命令，命令使用当前时间；持续收串口数据时仍给采样和控制留出机会。
- 新增 `RANGE? L/C/R` 逐路只读诊断和 `python -m host.range_check` CSV 记录工具。现有 `PONG 2`、`STAT` 字段保持兼容。

根据工程内 ST HAL 源码核对，`HAL_TIM_Base_Start` 与 `HAL_TIM_IC_Start_IT` 使用不同的状态检查，先启动计数器不会直接阻止捕获启动。HAL 的捕获停止会关闭计数器，驱动在停止后重新启用，避免 TIM10 灰度扫描时钟停掉。已对照现有初始化确认：

| 通道 | TRIG | Echo | 捕获 | PSC | 定时器输入时钟 | 中断 |
| --- | --- | --- | --- | --- | --- | --- |
| 左 L | PA1 | PF6 AF3 | TIM10 CH1 | 167 | 168 MHz | TIM1_UP_TIM10 |
| 中 C | PA5 | PF7 AF3 | TIM11 CH1 | 167 | 168 MHz | TIM1_TRG_COM_TIM11 |
| 右 R | PA7 | PF8 AF9 | TIM13 CH1 | 83 | 84 MHz | TIM8_UP_TIM13 |

计数单位都是 1 µs，ARR=65535。Echo 配置保持 V3.1 的直连/No Pull；没有凭缺失的模块手册更改硬件接线。

## 下午测量步骤

1. 烧录本次 `build/Debug/if_car.hex`（或 `.elf`），先保持 `IDLE`。检查接插件方向、模块型号、供电和共地。按 PINOUT 的 H1/H2 映射核对到实际 GPIO，不能只按排针位置估计。使用 `.bin` 时加载地址为 `0x08000000`。
2. 将平整硬物放在每只探头前约 10–30 cm，先在不驱动电机/舵机的情况下测。板端和模块端分别测对应 TRIG：预期约 12 µs 高脉冲；轮询时每只约 180 ms 一次。`triggers` 仅证明程序写过 GPIO，不能代替示波器检查波形。
3. 测模块 Echo 输出和 MCU PF6/PF7/PF8 输入：预期看到高电平脉冲。根据当前 343 m/s 换算，10/20/30 cm 约对应 583/1166/1749 µs，仅作台架粗查。实际模块的触发门限和 Echo 电平以实物手册及测量为准。
4. 在 GUI 串口页依次发送 `RANGE? L`、`RANGE? C`、`RANGE? R`；或退出 GUI 连接，运行 `python -m host.range_check --port COM3 --duration 30`，BLE 可用 `--ble BT24` 或实物蓝牙地址。日志默认保存在 `tmp/range_日期_时间.csv`。工具只读，不会启动或停止车辆。
5. 如果模块输出有 Echo 而 MCU 输入没有，检查信号线及载板网络。如果 MCU 输入已有 Echo，但 `rises/falls` 不增，检查 AF、CC1 捕获/中断以及是否烧录了当前固件。断开其他探头再测一只，可检查串音和共用供电影响；未接的通道会报告无效。

## 诊断解释

返回字段：`RANGE side state valid echo_high pulse_us distance_mm age_ms triggers rises falls timeouts errors counter prescaler flags timer_running`。

| 状态 | 含义 / 后续测量 |
| --- | --- |
| NEVER | 尚未轮到该通道触发。 |
| WAIT_RISE / WAIT_FALL | 本次等待中，观察一个以上轮询周期后再判断。等待时可使用上一有效距离；脉宽字段为本次尝试。 |
| OK | 收到合格的一对边沿；`valid=0` 时表示该结果已过期。 |
| NO_RISE | 30 ms 内未收到上升沿；检查供电、TRIG 和 Echo。此状态不能单独证明模块损坏。 |
| NO_FALL | 有上升沿但未收到下降沿；测 Echo 是否卡高或高电平超过截止时间。 |
| ECHO_HIGH | 触发前 Echo 已高，本次不触发；检查实际高电平与模块忙状态。 |
| START_ERROR | HAL 未能启动捕获；检查通道状态或是否被其他代码重复启动。 |
| BAD_PULSE | 脉宽不在当前 100–30000 µs 范围；保留原始脉宽供检查。 |
| OVERCAPTURE | CC1OF 置位，捕获被覆盖；检查噪声、串音或中断延迟。 |
| LATE_ECHO | 截止时间以后才进入捕获回调；检查模块输出及中断阻塞。 |
| IRQ_MISSED | 超时时 CC1/CC1OF 仍挂起，检查 NVIC/共享中断入口及阻塞原因。 |
| CLOCK_ERROR | 计数器/微秒延时异常；检查定时器时钟和 CEN，电机输出会被关断。 |

`valid=0` 时距离为 `-1`。`age_ms=4294967295` 表示还没有完成测量尝试。计数为上电以来累计值；`triggers` 是已启动捕获并实际写出触发高电平的次数，`rises/falls` 是驱动接受的边沿回调次数，`timeouts` 是截止时间失败次数，`errors` 是卡高、启动、脉宽、过捕获或延时错误次数。`flags` 为当前 SR 与本次失败时记录的标志合并，下一次尝试会清除旧记录；CC1 为 bit 1，CC1OF 为 bit 9。`timer_running` 只代表 CEN 已置位，不能单独证明计数器正在前进。

## 验证结果

`python tests/run_tests.py` 的 3 组 C 测试和 18 项 Python 测试全部通过。新增回归覆盖无回波不再视为空旷、等待期间上一值保留、卡高/缺下降沿、短脉冲、过捕获、迟到回调、挂起捕获中断、捕获启动失败、故障恢复、过期结果、定时器冻结时退出并禁止驱动、串口命令预算，以及无有效测距时实际 C 应用拒绝自动启动。

Debug/Release 交叉构建通过，Flash 分别为 60,916 / 44,716 字节，RAM 分别为 4,136 / 4,096 字节（含链接脚本预留）。两种构建均生成 HEX/BIN/ELF。日志工具以 `--simulate --duration 0.1` 完成一轮 L/C/R 记录，CSV 字段和协议诊断解析通过检查；仿真记录仅用于验证工具流程。`git diff --check` 通过。

本次检查未烧录或连接实物；台架波形、实物距离、电气门限、实际 BLE 连接与下午提供的例程仍待实测对照。
