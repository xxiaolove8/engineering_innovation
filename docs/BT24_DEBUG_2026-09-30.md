# BT24 蓝牙连接排查（2026-09-30）

本记录保存旧 DX-BT24 的联调历史。当前蓝牙已改为四针 JDY-31，使用 SPP 出站 COM；新模块适配与验证见 [MODULE_UPDATE_2026-09-30.md](MODULE_UPDATE_2026-09-30.md)。下述 BLE 特征值及实测结果不代表 JDY-31。

用户反馈：本地上位机连接 BT24 失败，但 [在线串口助手](https://serial.baud-dance.com/#/) 可以通过浏览器的蓝牙设备列表选择 BT24 并连接。本次按 BLE GATT 透传核对手册、网页助手和本地实现，分别检查蓝牙建链与小车固件握手。

## 手册与网页助手对照

工程内《蓝牙模块 AT 指令手册》版本 2.6，相关页码如下：

| 依据 | 内容 | 工程处理 |
| --- | --- | --- |
| 第 19 页，5.2.1 | 默认服务 UUID 为 `0xFFE0`。 | 使用 `0000ffe0-0000-1000-8000-00805f9b34fb`。 |
| 第 19 页，5.2.2 | 默认通知 UUID 为 `0xFFE1`，该通道也支持读写。 | 订阅 FFE1 通知，默认也向 FFE1 写入。 |
| 第 20 页，5.2.3 | 默认独立写入 UUID 为 `0xFFE2`。 | 保留 FFE2 可选配置；FFE1 不具备写入能力时可回退到 FFE2。 |
| 第 15–16 页，5.1.4–5.1.5 | 默认名称为 BT24；`AT+NAMAC` 可添加 MAC 后缀。 | 默认目标 BT24；实际名称或地址以扫描结果为准。 |
| 第 16–17 页，5.1.6–5.1.10 | 默认 1 停止位、无校验、9600 波特率、流控关闭、透传开启。 | STM32 USART3 使用 9600、8N1、无流控。BLE 建链成功后仍需核对模块 UART 配置。 |
| 第 14 页，4.1 | AT 指令以 CRLF 结尾。 | 这是模块配置指令要求；小车 ASCII v2 命令由 STM32 处理，按工程协议以 LF 结尾。 |

网页助手的“通用Ⅰ型”默认使用 **FFE0 服务、FFE1 收发**，写入时优先采用不带响应的 GATT 写入。核对依据为其公开源码：[通道配置 useBleStore.js](https://github.com/BaudDance/SerialAssistant/blob/main/src/store/useBleStore.js)、[GATT 实现 bleGatt.js](https://github.com/BaudDance/SerialAssistant/blob/main/src/utils/bleGatt.js)。本次还核对了 [网页部署脚本](https://serial.baud-dance.com/assets/index-btd1rCvd.js)，配置一致；部署脚本文件名可能随网页版本更新。

旧程序优先 FFE2，且当特征同时声明两种写入能力时优先带响应写入。此路径符合模块手册，但与网页助手默认路径不同。目前改为 FFE1 默认、优先不带响应写入；保留 FFE2 选择和按特征能力回退，写入继续分成不超过 20 字节的块。此修改用于对齐已知可连接的网页配置，不能单独证明旧写入方式就是本次失败根因。

## 实物 GATT 检查

本次实际读取到以下服务与特征：

| UUID | 实物声明属性 |
| --- | --- |
| FFE0 | 透传服务 |
| FFE1 | `read`、`notify`、`write-without-response`、`write` |
| FFE2 | `write-without-response`、`write` |

这确认实物提供手册中所述的两个写入通道。读取 GATT 服务和特征不代表 STM32 已收到命令，也不代表 `PING` 已返回 `PONG 2`。固件往返通讯结果见下方验证记录。

## 用户操作

1. 在在线串口助手中断开 BT24，再使用本地上位机。避免网页和本地程序同时占用连接。
2. 从工程目录启动 `start_gui.cmd`。该入口使用工程 `.venv`，本次已安装依赖，无需依赖系统 `python` 指向哪个解释器。在 PowerShell 中可运行：

   ```powershell
   cd D:\projects\if_car
   .\start_gui.cmd
   ```

3. 设备目标填写 `BT24`，通道选择 **FFE1（网页通用Ⅰ型）**，点击连接。界面会分别报告扫描、GATT 建链、通知订阅以及固件 `PING` 握手，并记录原始回复。
4. 如果扫描未找到设备，核对广播名称、地址和模块供电；如果 GATT 或通知步骤失败，保留具体阶段与原始错误。只有 `PING` 返回 **`PONG 2`** 才代表本工程固件握手通过。
5. 如果 GATT 建链与通知订阅成功，但 `PING` 没有返回 `PONG 2`，核对模块端 UART 是否为 **9600、8N1、无流控**，透传是否开启，是否共地，TX/RX 是否交叉连接，以及是否烧录当前协议 v2 固件。工程接线为 STM32 **PB10 / USART3_TX → BT24 RX**，**PB11 / USART3_RX ← BT24 TX**。保留实际收到的文本；旧固件回复与完全没有回复需要分别处理。
6. 如果需要与网页对照，先断开本地连接，再在网页通用Ⅰ型中发送 ASCII `PING` 并追加 LF，查看是否收到 `PONG 2`。网页仅显示“已连接”不能证明这一步已经成功。

也可在关闭其他 BT24 连接后运行独立诊断：

```powershell
cd D:\projects\if_car
.\.venv\Scripts\python.exe -m host.ble_check --target BT24
```

只检查扫描、GATT 和通知订阅，暂不要求固件握手：

```powershell
.\.venv\Scripts\python.exe -m host.ble_check --target BT24 --transport-only
```

`--transport-only` 成功只说明蓝牙传输层检查通过。完整诊断还需要小车协议往返响应。保留输出中的失败阶段、UUID、特征属性和原始回复，便于继续定位。

## 通信与执行器初始化解耦

旧应用把 UART 收发启动与测距定时器、PWM、编码器启动放在同一初始化流程中。执行器或微秒定时器启动失败时，应用会初始化失败，导致即使 BT24 已建立 GATT 连接，也无法通过主循环处理 `PING`。代码审查已确认这条失去诊断通道的路径；尚未证明现场恰好发生了此故障。

目前先启动 UART 通信，再启动测距定时器、舵机/电机 PWM 和编码器。UART 启动成功后，即使这些外设启动失败，应用仍处理通信，并保持 `FAULT`、**fault=6（硬件初始化/定时器异常）**、电机停机。`AUTO ARM`、`DEBUG`、`DRIVE` 返回 `ERR HARDWARE`；`STOP` 仍可应答，但不会清除硬件故障。修正原因后需重新上电验证。UART 本身初始化失败、进入硬故障或更早的系统初始化失败不在这一可通信保证内。

新增只读命令 **`HW?`**，回复 `HW ready stage`。正常为 `HW 1 READY`，失败例如 `HW 0 CLOCK`。GUI 会显示硬件初始化状态和失败阶段；协议 v2 握手继续使用 `PING` → `PONG 2`，较早的 v2 固件可以连接，但可能不支持 `HW?`。

| stage | 含义 |
| --- | --- |
| NEVER | 尚未完成应用硬件初始化。 |
| RANGE_L / RANGE_C / RANGE_R | 对应测距定时器启动失败。 |
| CLOCK | 微秒计时器未前进，或运行中检测到计时异常。 |
| SERVO_PWM | 舵机 PWM 启动失败。 |
| MOTOR_L_PWM / MOTOR_R_PWM | 对应电机 PWM 启动失败。 |
| ENCODER_L / ENCODER_R | 对应编码器启动失败。 |
| READY | 当前应用硬件检查已就绪。 |

`HW 1 READY` 表示软件启动与计时检查通过，不能替代超声波波形、编码器方向或实际电机/舵机动作的验收。连接成功后，可在串口信息页发送 `HW?` 与 `STATUS?`；若出现 fault=6，先依据 stage 检查该外设。

## ST-Link 只读检查记录

为进一步读取 MCU 状态，另行检查了电脑与 ST-Link 的连接。初次 Windows PnP 能枚举 `0483:3748`，状态正常、错误码 0，绑定 WinUSB，接口 GUID 与 ST 官方驱动 INF 一致。但 `STM32_Programmer_CLI -l stlink-only -vb 3` 报 `DEV_CONNECT_ERR`、固件版本为空；该命令仅枚举探针，不访问目标 SWD，因此此时先调查探针 USB 命令/识别通路。

原始 WinUSB 打开和标准 USB 描述符读取成功。设备具有 bulk `0x81`、`0x02`、`0x83` 端点，序列号描述符长 26 字节，包含非 ASCII 字符，低字节可重构为 `37FF71064E57343664B11343`；CLI 初次却显示 Windows 位置实例号。开源 stlink 的 [序列号处理代码](https://github.com/stlink-org/stlink/blob/develop/src/stlink-lib/usb.c#L1061) 为这类 26 字节格式提供兼容处理。这些是识别/兼容风险的排查证据，不足以判定本次失败由该格式造成，也不表示 WinUSB 驱动没有工作。

用户重新插拔 ST-Link USB 后，同一仅枚举命令恢复真实序号 **`37FF71064E57343664B11343`** 与固件 **`V2J46S7`**。此前 USB 命令/识别异常已在重插后恢复；尚未确定其具体原因。这项结果与 BT24 的 BLE 连接属于两条不同链路，不据此认定蓝牙或目标 SWD 故障根因。MCU 的后续只读结果见下方验证表；本记录不将 USB 枚举恢复等同于 MCU 读取成功。

## 其他配置影响

AT 手册第 22 页说明，私有密码功能默认关闭；若启用，主机需要在连接后 7 秒内认证，否则模块自动断开。第 25 页说明连接状态通知默认关闭，开启后会向 UART 输出连接信息。只有实际配置或日志表明这些功能启用时，再针对性检查。不要为排查连接问题直接恢复出厂或清除所有广播参数。

Windows GATT 缓存也可能影响服务读取，相关接口说明见 [Bleak WinRT 官方参数文档](https://bleak.readthedocs.io/en/latest/_modules/bleak/args/winrt.html)。应结合具体服务读取错误和诊断输出判断，不能把缓存作为已确认根因。
